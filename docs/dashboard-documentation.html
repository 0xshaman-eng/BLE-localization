BLE Tool Tracking System – Web Dashboard

Complete documentation for the web-based dashboard that displays tool locations, manages tool registrations, and handles tag mapping. The dashboard communicates with the same Firebase database used by the Android application.

1. Dashboard Overview

The dashboard is a single-page web application that provides a real-time view of all tracked tools. It connects to the same Firebase Realtime Database that the Android app writes to, so changes made by the app (new sightings, location updates) appear on the dashboard within milliseconds.

What is a Single-Page Application (SPA)? A web application that loads one HTML page and dynamically updates its content using JavaScript, without reloading the entire page. The dashboard is a simple SPA — it consists of one index.html file and one app.js file.

Key Capabilities

  • Real-time tool tracking — see tool locations update live on the map
  • Tool management — add, delete, map/unmap tags
  • Multi-anchor winner selection — automatically picks the best location when multiple phones detect the same tag
  • Advanced filtering — search by name, tag ID, date range, or map bounds
  • Multi-tag-type support — handles Hilti (decimal), ELA (C ID), EM (MAC), and is extensible for new tag types

3.1 Firebase Connection

The dashboard connects to Firebase using the same project as the Android app. The configuration is embedded directly in app.js:

const firebaseConfig = {
    apiKey: window.__FIREBASE_API_KEY__,
    authDomain: window.__FIREBASE_AUTH_DOMAIN__,
    databaseURL: window.__FIREBASE_DATABASE_URL__,
    projectId: window.__FIREBASE_PROJECT_ID__,
    storageBucket: window.__FIREBASE_STORAGE_BUCKET__,
    messagingSenderId: window.__FIREBASE_MESSAGING_SENDER_ID__,
    appId: window.__FIREBASE_APP_ID__,
    measurementId: window.__FIREBASE_MEASUREMENT_ID__
};

const app = initializeApp(firebaseConfig);
const db = getDatabase(app);
What are these config values? They identify which Firebase project to connect to. These values are loaded from public/env.js (see README for setup). Security is controlled by Firebase Security Rules on the server side.

3.2 Database References

const toolsRef = ref(db, "ble-localization-poc/tools");
const sightingsRef = ref(db, "ble-localization-poc/sightings");

These are the same paths the Android app reads/writes. Both sides share a single source of truth.

3.3 Real-time Listeners

What is onValue? A Firebase function that sets up a persistent listener. Whenever data at the specified path changes (any child added, modified, or removed), the callback fires with the entire updated snapshot. This is how the dashboard stays in sync without polling.

Tools Listener

onValue(toolsRef, (snapshot) => {
    const data = snapshot.val();
    tools = data
        ? Object.keys(data).map(key => ({ id: key, ...data[key] }))
        : [];

    // Update connection indicator
    statusDot.classList.add("connected");
    statusText.textContent = `Connected - ${tools.length} tool(s)`;

    computeWinners();   // Re-calculate best location per tool
    applyFilters();     // Re-render UI with current filters
});

Sightings Listener

onValue(sightingsRef, (snapshot) => {
    const data = snapshot.val();
    sightings = data
        ? Object.keys(data).map(key => ({ id: key, ...data[key] }))
        : [];

    // Recompute winners when sightings change
    if (tools.length > 0) {
        computeWinners();
        applyFilters();
    }
});
Firebase Database changes │ ├─── tools node changed ──▶ onValue callback │ ├─ Update tools array │ ├─ computeWinners() │ └─ applyFilters() → renderTools() + updateMap() │ └─── sightings node changed ──▶ onValue callback ├─ Update sightings array ├─ computeWinners() └─ applyFilters() → renderTools() + updateMap()

3.4 Error Handling

If the Firebase connection fails, the status indicator turns red and displays the error message. The listeners include an error callback:

onValue(toolsRef, successCallback, (error) => {
    statusDot.classList.remove("connected");
    statusText.textContent = "Error: " + error.message;
});

4.2 Tool Object Structure

Each tool object in the tools array has these fields. Fields come from Firebase, plus a computed object added by the winner algorithm:

{
    id:             "firebase-auto-key",   // Firebase push key
    name:           "Hammer Drill",        // User-defined name
    tagUuid:        "d32218666c12",        // Mapped tag ID (or null)
    tagType:        "hilti",               // "hilti" | "ela" | "em"

    // Raw data written by the Android app:
    lastLat:        6.927079,              // GPS latitude (0 = unknown)
    lastLng:        79.861244,             // GPS longitude
    lastSeenAt:     1716100234567,         // Timestamp (ms)
    lastRssi:       -55,                   // Signal strength (dBm)
    lastAnchorId:   "uuid",                // Reporting phone's UUID
    lastAnchorName: "Anchor-Pixel6",       // Reporting phone's name

    // Computed by winner selection (added client-side):
    computed: {
        lat:        6.927079,              // Best location latitude
        lng:        79.861244,             // Best location longitude
        timestamp:  1716100234567,         // Best sighting time
        rssi:       -55,                   // Strongest signal
        anchorId:   "uuid",                // Winning anchor's UUID
        anchorName: "Anchor-Pixel6",       // Winning anchor's name
        windowSize: 3                      // Number of candidates in window
    }
}
Why computed? When multiple phones detect the same tag, each writes its own sighting. The computed object holds the winner — the location from the phone with the strongest signal within a 1-second time window. The dashboard prefers computed data over raw lastLat/lastLng for display.

5. Winner Selection Algorithm

When multiple Android phones (anchors) detect the same BLE tag, each one writes a sighting to Firebase with its own GPS location. The dashboard must decide which sighting represents the best estimate of the tool's position. This is the winner selection algorithm.

What is RSSI? Received Signal Strength Indicator — a measure of how strong a wireless signal is when received. Measured in dBm (decibels relative to one milliwatt). Values are negative: -40 dBm is a very strong signal (tag is nearby), -90 dBm is very weak (tag is far away). The closer to zero, the stronger the signal and the more accurate the position estimate.

5.1 Algorithm Steps

For each tool with a tagUuid: ┌─────────────────────────────────────────────────────────────┐ │ 1. Filter all sightings where tagUuid matches the tool's │ │ │ │ 2. Sort by timestamp descending (most recent first) │ │ │ │ 3. Get the most recent sighting's timestamp (T_max) │ │ │ │ 4. Collect all sightings within [T_max - 1000ms, T_max] │ │ (the "time window") │ │ │ │ 5. Among those in the window, pick the one with the │ │ highest RSSI (strongest signal = closest phone) │ │ │ │ 6. Store the winner's data in tool.computed: │ │ { lat, lng, timestamp, rssi, anchorId, anchorName, │ │ windowSize } │ └─────────────────────────────────────────────────────────────┘

5.2 Why This Works

  • Time window ensures only recent, concurrent sightings are compared — not stale data from minutes ago
  • Strongest RSSI picks the phone that was closest to the tag, which has the most accurate GPS position for it
  • No coordination needed — each phone writes independently; the dashboard resolves conflicts automatically

5.3 Worked Example

Scenario: Two phones detect the same tag within 300ms of each other.
SightingAnchorTimestampRSSILocation
APixel 610:00:00.500−55 dBm(6.927, 79.861)
BSamsung S2310:00:00.800−70 dBm(6.928, 79.862)

Step 3: Most recent = 10:00:00.800 (Sighting B)

Step 4: Window = [10:00:00.000, 10:00:00.800] → Both A and B qualify

Step 5: Compare RSSI: −55 > −70 → Sighting A wins

Result: Tool location = (6.927, 79.861) from Pixel 6

5.4 Code

function computeWinners() {
    tools.forEach(tool => {
        if (!tool.tagUuid) { tool.computed = null; return; }

        // Get sightings for this tool's tag
        const tagSightings = sightings
            .filter(s => s.tagUuid === tool.tagUuid)
            .sort((a, b) => (b.timestamp || 0) - (a.timestamp || 0));

        if (tagSightings.length === 0) { tool.computed = null; return; }

        const mostRecentTime = tagSightings[0].timestamp || 0;

        // Find all sightings within the 1-second window
        const withinWindow = tagSightings.filter(s =>
            mostRecentTime - (s.timestamp || 0) <= STRONGEST_WINDOW_MS
        );

        // Pick the one with strongest RSSI
        let winner = withinWindow[0];
        withinWindow.forEach(s => {
            if ((s.rssi || -100) > (winner.rssi || -100)) winner = s;
        });

        tool.computed = {
            lat: winner.anchorLat, lng: winner.anchorLng,
            timestamp: winner.timestamp, rssi: winner.rssi,
            anchorId: winner.anchorId, anchorName: winner.anchorName,
            windowSize: withinWindow.length
        };
    });
}

7. Filtering System

The dashboard provides a multi-layered filtering pipeline that narrows down the displayed tools. Filters are combined — each one further reduces the list produced by the previous filter.

What is a Filtering Pipeline? A chain of filter steps applied one after another. The full list of tools enters at the top, each filter removes tools that don't match, and only the survivors reach the bottom (and get displayed). All filters are applied every time any single filter changes.

Tag UUID filter │ Matches display format AND raw storage format └────────────┬────────────┘ │ ▼ ┌─────────────────────────┐ │ 3. Date Range filter │ From/To datetime + "include missing" toggle └────────────┬────────────┘ │ ▼ ┌─────────────────────────┐ │ 4. Map Bounds filter │ Only tools visible in current map viewport └────────────┬────────────┘ │ ▼ filteredTools │ ┌────────┴────────┐ ▼ ▼ renderTools() updateMap()

7.2 Date Range Filter

  • From / To: datetime-local inputs that define a time window
  • Include missing: Checkbox — if checked, tools with no lastSeenAt are included despite the date filter
  • Default behaviour: When no date range is set and "include missing" is unchecked, tools without lastSeenAt are excluded

7.3 Geographic Filter (Map Bounds)

What is Debouncing? A technique that delays executing a function until the user stops performing an action. When you pan the map, the moveend event fires many times. Debouncing waits 300ms after the last event before applying the filter, preventing excessive re-renders.
  • Toggle: "Filter by current map bounds" checkbox
  • Logic: Only shows tools whose coordinates fall within the visible map rectangle
  • Auto-update: When enabled, filters re-apply after every map pan or zoom (debounced at 300ms)
  • Excludes: Tools with lastLat == 0 && lastLng == 0 (no location)

8.3 Marker Updates

The updateMap() function is called whenever filteredTools changes:

  1. Remove stale markers — markers for tools no longer in the filtered list are removed
  2. Create/update markers — for each tool with a valid location:
    • Use computed coordinates if available (winner selection), otherwise fall back to raw lastLat/lastLng
    • Recreate the marker each time to ensure the icon colour is correct
    • Bind a popup with tool name, tag UUID, last seen time, RSSI, and anchor name

9. Tool Management

9.1 Adding a Tool (Dashboard)

The "Add Tool" tab provides a form that creates a tool and maps a tag in one step:

  1. Enter the tool name (required)
  2. Select the tag type (Hilti, ELA, or EM) from a dropdown
  3. Enter the tag ID using the segmented input (see §10)
  4. Submit → the dashboard:
    • Converts the tag ID to storage format (formatTagForStorage())
    • Checks for duplicate tags (scans tools array)
    • Writes to Firebase with push() + set()
// What gets written to Firebase on "Add Tool":
{
    name:       "Hammer Drill",
    tagType:    "hilti",
    tagUuid:    "d322126c6618",   // Converted from decimal input
    lastLat:    0,
    lastLng:    0,
    lastSeenAt: null
}

9.2 Deleting a Tool

From the 3-dot menu (⋮) on any tool card:

  1. Click "Delete"
  2. Confirm dialog: "Delete «Tool Name»? This cannot be undone."
  3. If confirmed → remove(ref(db, 'ble-localization-poc/tools/{toolId}'))
  4. Firebase listener automatically removes the tool from the UI

9.3 Unmapping a Tag

From the 3-dot menu:

  1. Click "Unmap Tag" (only visible if a tag is mapped)
  2. update(ref(db, ...), { tagUuid: null })
  3. The tool remains but is no longer linked to any BLE tag
  4. The Android app will stop updating this tool's location

9.4 Locating a Tool

Clicking anywhere on a tool card (except the menu) calls locateTool(toolId):

  1. Finds the tool in the tools array
  2. Gets coordinates (prefers computed, falls back to raw)
  3. Sets highlightedToolId → triggers red marker
  4. Zooms map to the tool's location at zoom level 18
  5. Opens the marker's popup

10. Tag Input & Format Conversion

10.1 Segmented Tag Input

The "Add Tool" form uses a specialised segmented input for entering tag IDs — each character gets its own box, similar to how OTP codes are entered. The behaviour changes depending on the selected tag type:

What is a Segmented Input? A series of individual single-character text boxes arranged in a row. Each box accepts exactly one character, and the cursor automatically advances to the next box after typing. This prevents formatting errors and makes it clear exactly how many characters are expected.
Tag TypeTotal SegmentsPrefixEditableInput ModeAllowed Characters
Hilti9None9 digitsNumeric keyboard[0-9]
ELA9"C", "I", "D" (3 boxes, greyed out)6 hex charsText keyboard[0-9A-F]

Configuration

const TAG_INPUT_CONFIG = {
    hilti: {
        totalSegments: 9,
        prefixSegments: 0,
        inputMode: 'numeric',
        allowedPattern: /[0-9]/
    },
    ela: {
        totalSegments: 9,
        prefixSegments: 3,       // "C", "I", "D" are pre-filled and read-only
        inputMode: 'text',
        allowedPattern: /[0-9A-F]/
    }
};

Input Behaviour

  • Auto-advance: After typing a valid character, focus moves to the next box
  • Backspace: If the current box is empty, moves focus to the previous box and clears it
  • Arrow keys: Left/Right to navigate between boxes
  • Paste: Distributes pasted text across boxes starting from the current one
  • Validation: Only allowed characters are accepted; others are silently rejected
  • Uppercase: ELA hex characters are automatically uppercased

10.2 Format Conversion Functions

Display Format (formatTagForDisplay)

Converts a stored tag UUID to the human-readable format shown in the UI:

Storage Format (formatTagForStorage)

Converts user input from the segmented input to the format stored in Firebase:

Tag TypeUser InputStored ValueConversion
Hilti309257752d322126c6618Decimal to hex → pad → reverse bytes → add d322
ELA015E58C ID 015E58Prefix with "C ID "

Type Inference (inferTagType)

Determines the tag type from its stored UUID: if it starts with "C ID " → ELA, if exactly 12 hex chars and matches MAC pattern → EM, otherwise → Hilti. Used when tagType is not explicitly stored on the tool.

What is push()? A Firebase method that generates a unique key (like -NxYz123abc) and creates a new child node under the specified path. The key is guaranteed to be unique and is sorted chronologically. set() then writes the data to that new key.

11.6 XSS Prevention

What is XSS? Cross-Site Scripting — a security vulnerability where an attacker injects malicious JavaScript into a web page through user input. For example, if a tool name contained <script>alert('hacked')</script>, it could run when displayed.

All user-provided strings (tool names, tag UUIDs) are escaped before being inserted into HTML using the escapeHtml() function:

function escapeHtml(str) {
    const div = document.createElement("div");
    div.textContent = str || "";
    return div.innerHTML;  // Automatically escapes <, >, &, etc.
}
