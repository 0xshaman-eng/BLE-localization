BLE Tool Tracking System – Android Application

Complete architectural documentation for the Android BLE scanning application that detects, identifies, and tracks physical tools fitted with BLE tags. This system is designed to support many types of BLE tags — not just one vendor.

What is BLE? Bluetooth Low Energy is a wireless technology that lets small battery-powered devices (called tags) broadcast tiny packets of data. A nearby phone can pick up these broadcasts, identify the tag, and record where and when it was seen.

1. System Overview

This application is one half of a two-part system for tracking physical tools (drills, hammers, grinders — any equipment) on job sites. Each tool is fitted with a small BLE tag that continuously broadcasts a unique identifier. The Android app runs in the background, listens for these broadcasts, determines the phone's GPS location, and uploads both pieces of data to a cloud database. A separate web dashboard then displays all tools on a live map.

The system is designed to support many types of BLE tags from different manufacturers. Currently two tag families are implemented (Hilti and ELA), but the architecture makes adding new tag types straightforward — just write a new packet parser and add a scan filter.

Anchor: Each Android phone running the app is called an anchor. Multiple anchors can be deployed across a large site; each one independently detects tags in its vicinity and reports them. The dashboard then picks the best report using a winner selection algorithm.

3.4 Battery Optimisation Exemption

What is Battery Optimisation? Android aggressively limits what apps can do in the background to save battery. The app requests an exemption so scanning can continue. Without this, the system may pause the service after minutes of inactivity.

On first launch, MainActivity requests ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS. This shows a system dialog; the request is made only once.

3.5 Service Persistence

  • START_STICKY — tells Android to restart the service if it's killed for memory
  • onTaskRemoved() — if the user swipes the app away, the service restarts itself
  • onResume() — when the app comes to the foreground, ensureServiceRunning() re-starts the service if stopped

4. BLE Scanning Architecture

What is a Scan Filter? A scan filter tells the Android Bluetooth stack: "Only notify me about BLE devices that match these criteria." By filtering on a manufacturer's registered numeric ID, the app only receives packets from known tag types. This also enables scanning when the screen is off (see §4.1).

4.1 Why Manufacturer Filters Are Required

Starting with Android 8.1, the operating system blocks unfiltered BLE scans when the screen is off. If you start a scan without filters, it silently stops producing results the moment the screen turns off. By providing ScanFilter objects, the Bluetooth hardware (not the CPU) continues matching packets, so scanning works even in deep sleep.

Current filters:
  1. Hilti filter – Manufacturer ID 780 (0x030C)
  2. ELA filter – Manufacturer ID 1879 (0x0757)
  3. EM filter – Manufacturer ID 90 (0x005A)
  4. Test filter – Manufacturer ID 67 (development)

To add a new tag type, create ScanFilter.Builder().setManufacturerData(NEW_ID, byteArrayOf()).build() and add it to the filter list.

4.2 Scan Settings

What are Scan Settings? They control how aggressively the Bluetooth radio scans:
  • LOW_POWER – scans infrequently; best battery life but slow detection
  • BALANCED – moderate rate
  • LOW_LATENCY – scans as fast as possible; more battery but detects tags within milliseconds
This app uses LOW_LATENCY because timely detection is critical for accurate tracking. 
val scanSettings = ScanSettings.Builder()
    .setScanMode(ScanSettings.SCAN_MODE_LOW_LATENCY)  // Fastest detection
    .setReportDelay(0)                                // Report each result immediately
    .build()

setReportDelay(0) means each detected packet triggers the callback immediately rather than being batched by the hardware.

4.4 BLE Tracking Service

What is a Foreground Service Type? Android 14+ requires services to declare what they do. This app declares:
  • CONNECTED_DEVICE – it communicates with Bluetooth hardware
  • LOCATION – it accesses GPS

BleTrackingService is a LifecycleService that:

  1. Creates a notification channel and shows a persistent notification ("Scanning for tags…")
  2. Injects and starts BleTagDetector
  3. Manages three periodic jobs:
    • BLE Scan Restart – every 60 seconds, stops and restarts the scan to work around Android silently stopping long-running scans
    • WakeLock Refresh – every 8 minutes, releases and re-acquires the WakeLock
    • Screen state monitoring – a ScreenOffReceiver updates the notification text when the screen toggles

4.5 WakeLock Management

What is a WakeLock? When the screen is off, Android puts the CPU into low-power sleep. A WakeLock tells the system: "Keep the CPU running." Without it, the BLE scan callback stops being invoked. A PARTIAL_WAKE_LOCK keeps the CPU on but lets the screen stay off — the most battery-efficient option that still allows scanning. 
val wakeLock = powerManager.newWakeLock(
    PowerManager.PARTIAL_WAKE_LOCK,
    "BLETrackingService:WakeLock"
)
wakeLock.acquire(10 * 60 * 1000L) // 10-minute timeout

Because Android may release WakeLocks after their timeout, the service refreshes every 8 minutes (release → wait 1 second → re-acquire), creating overlapping 10-minute windows for continuous CPU availability.

5. Packet Parsing & Tag Identification

Each BLE tag type broadcasts data in a different format. A packet parser reads raw bytes from a BLE advertisement and extracts a unique tag identifier. Adding support for a new tag family means writing a new parser.

5.1 Hilti Packet Parser

What is Manufacturer Specific Data? BLE advertisements can contain a section of bytes defined by the tag manufacturer. The first 2 bytes are a registered company ID (e.g. 780 for Hilti). The remaining bytes hold whatever the manufacturer chose — in Hilti's case, a 6-byte tag UUID.
FieldValue
Manufacturer ID780 (0x030C)
Minimum payload8 bytes
UUID locationBytes 2–7 (6 bytes)
UUID format12-character lowercase hex string
// Example: Manufacturer data = [.., .., 0xd3, 0x22, 0x18, 0x66, 0x6c, 0x12]
//   Bytes 2-7 → d3 22 18 66 6c 12 → Tag UUID: "d32218666c12"

object HiltiPacketParser {
    const val MANUFACTURER_ID = 780

    fun parse(manufacturerData: ByteArray): HiltiPacket? {
        if (manufacturerData.size < 8) return null
        val uuidBytes = manufacturerData.copyOfRange(2, 8)
        val tagUuid = uuidBytes.joinToString("") { "%02x".format(it) }
        return HiltiPacket(tagUuid)
    }
}

5.2 ELA Packet Parser

ELA Blue Coin tags use a different structure. The manufacturer data contains a DataInfo byte, and the actual tag ID is carried in the BLE advertisement's Complete Local Name (a human-readable string broadcast by the tag).

FieldValue
Manufacturer ID1879 (0x0757)
DataInfo byte (offset 0)0x06 (ID format devices)
Tag ID sourceBLE device local name (e.g. "CID015E58")
Normalised formatC ID 015E58
object ElaPacketParser {
    const val MANUFACTURER_ID = 1879

    fun parse(mfcData: ByteArray, scanRecord: ScanRecord?): ElaPacket? {
        if (mfcData[0] != 0x06.toByte()) return null   // Check DataInfo
        val localName = scanRecord?.deviceName ?: return null
        val normalised = normalizeCId(localName) ?: return null
        return ElaPacket(tagId = normalised)
    }
}

C ID Normalisation

The normalizeCId() function accepts several input formats and converts them all to "C ID XXXXXX":

InputOutputValid?
015E58C ID 015E58Yes
CID015E58C ID 015E58Yes
cid015e58C ID 015E58Yes
C ID 015E58C ID 015E58Yes
XYZnullNo — invalid

Validation requires exactly 6 hex characters matching [0-9A-F]{6}.

5.3 EM Packet Parser

EM Microelectronic tags use the AltBeacon format. The tag's MAC address is extracted directly from the Bluetooth device link-layer address (since the payload might truncate the full MAC).

FieldValue
Manufacturer ID90 (0x005A)
Signature bytes0xBE, 0xAC
Tag ID sourceBLE device link-layer MAC address
Normalised format12-character uppercase hex string (e.g. 58C35608EEB0)
object EmPacketParser {
    const val MANUFACTURER_ID = 90

    fun parse(manufacturerData: ByteArray, device: BluetoothDevice?): EmPacket? {
        if (!isAltBeaconFormat(manufacturerData)) return null
        val protocolMac = device?.address ?: return null
        val macHex = protocolMac.replace(":", "").uppercase()
        return EmPacket(tagId = macHex)
    }
}

5.4 Adding a New Tag Type

  1. Create NewTagParser.kt with a parse() method extracting the unique ID from manufacturer data
  2. Add a ScanFilter in BleTagDetector.startScanning() for the new manufacturer ID
  3. Add a branch in scanCallback.onScanResult() to call your parser when the manufacturer ID matches
  4. Add display/storage format helpers in both the app and the dashboard
  5. Add the tag type option to the dashboard's "Add Tool" form

6. Batch Processing & Location Updates

Rather than uploading to Firebase every time a BLE packet arrives (which could be hundreds per second), the app accumulates detections and processes them in 5-second batches.

6.1 Data Structures

What is a ConcurrentHashMap? A thread-safe dictionary. BLE callbacks run on a Bluetooth thread while batch processing runs on a separate scheduled thread. A ConcurrentHashMap allows both threads to read and write safely without corrupting data or crashing.

6.3 Adaptive Location Updates

GPS is battery-expensive. The app uses an adaptive strategy: it only requests GPS when it's actually detecting mapped tags.

┌─────────────────┐ Mapped tag │ GPS Updates │ No mapped tags detected ──▶ │ RUNNING │ ──▶ Idle counter++ │ (every 5 sec) │ └────────┬────────┘ │ idle ≥ 2 cycles? │ YES ▼ ┌─────────────────┐ │ GPS Updates │ Mapped tag │ STOPPED │ ◀── detected │ (save battery) │ └─────────────────┘
  • Start: A mapped tag appears in a batch cycle
  • Stop: 2 consecutive cycles with zero mapped tags (≈ 10 seconds idle)
  • Interval: 5 seconds via FusedLocationProviderClient.getCurrentLocation(HIGH_ACCURACY)
  • Caching: Latest location stored in lastKnownLocation, used for all tags in the next batch

Why both? The tool update gives the dashboard the latest position. The sighting log provides a history that the dashboard uses for multi-anchor winner selection — when multiple phones detect the same tag, the dashboard picks the strongest signal.

6.5 Unmapped Tag Notification

When a tag is detected that doesn't match any tool, the app shows a notification: "Tag X is not mapped to any tool." These are throttled to one per tag per 30 seconds to prevent spam.

7.3 Tag Cache (In-Memory)

To avoid querying Firebase on every BLE detection, BleTagDetector maintains an in-memory cache called mappedTags (Map<String, String> mapping tagUuid → toolId). This cache is kept in sync via:

  • Real-time listener: A Firebase ValueEventListener on the tools node updates the cache automatically
  • Manual refresh: refreshTagCache() is called at service startup and after any tag mapping operation

8. Tag UUID Encoding & Decoding

Hilti tags have a complex encoding because their barcodes show a decimal number, but the BLE broadcast contains hexadecimal bytes in little-endian order. Both the app and dashboard must convert between these formats identically.

What is Little-Endian? A way of ordering bytes where the least significant byte comes first. The number 0x18666C12 stored in little-endian becomes 12 6C 66 18. This is the opposite of how humans normally write numbers (most significant first). Many hardware protocols use little-endian because processors read the smallest part first.

8.3 Conversion Code (Android)

// Decimal barcode → Storage UUID
fun encodeBarcodeToTagUuid(decimalBarcode: String): String {
    val hex = decimalBarcode.toLong().toString(16).padStart(8, '0')
    val reversed = hex.chunked(2).reversed().joinToString("")
    return "d322$reversed"
}

// Storage UUID → Display decimal
fun hexToDecimal(hexUuid: String): String {
    val withoutPrefix = hexUuid.removePrefix("d322")
    val reversed = withoutPrefix.chunked(2).reversed().joinToString("")
    return reversed.toLong(16).toString()
}

9.5 BarcodeScanScreen

What is a Consensus Algorithm (in this context)? Instead of trusting a single barcode read (which might be wrong due to blur or glare), the app requires 5 consecutive identical reads before accepting the result. If they disagree, it resets and tries again. This dramatically reduces misreads.

Uses CameraX for the live camera feed and Google ML Kit for barcode detection:

  • Viewfinder overlay: Semi-transparent background with a clear window and crosshair
  • Centre targeting: Only considers the barcode closest to the screen centre
  • ISO-8859-1 fallback: Re-encodes barcodes with wrong character set (common with Data Matrix codes)
  • Digit extraction: Strips non-numeric characters from the barcode value
  • Consensus: 5 identical reads → accept; disagreement → reset
  • Feedback: Audio beep + haptic vibration on success; error tone on failure
  • Duplicate check: Blocks assignment if tag is already mapped to another tool

10. Dependency Injection (Hilt)

What is Dependency Injection (DI)? Instead of each class creating its own dependencies (e.g. a database connection), a central system provides them. Benefits: (1) objects can be shared (one database connection for the whole app), (2) code is easier to test because you can swap in fakes. Hilt is Google's recommended DI framework for Android — you annotate classes with @Inject and Hilt automatically creates and delivers the right objects.
What is a Singleton? An object created once and reused everywhere. For example, there is only one BleTagDetector in the entire app — the foreground service and the UI screens all share the same instance. This is critical because the scanner maintains state (tag cache, pending tags, session tags) that must be consistent.

11. Data Layer & ViewModels

11.1 Tool Entity

What is a Data Class? In Kotlin, a data class is a class whose main purpose is to hold data. Kotlin automatically generates equals(), hashCode(), toString(), and copy() methods. copy() is especially useful — it creates a new object with some fields changed while keeping the rest.

)

11.2 ToolRepository

What is a Repository? A design pattern that acts as a single source of truth for data. All database operations go through the repository, so the rest of the app doesn't need to know whether data comes from Firebase, a local cache, or anywhere else.

What is a Flow? A Kotlin Flow is a stream of values that arrive over time. Think of it like a pipe: Firebase pushes new data in one end, and the UI automatically updates at the other end. Unlike a one-time query, a Flow stays connected and delivers updates in real time.

11.3 ViewModels

What is a ViewModel? A class that stores and manages UI-related data. It survives configuration changes (like screen rotation) so data isn't lost. ViewModels contain business logic ("start a scan", "map a tag") while Composable screens only handle display.

TagMappingViewModel

  • Scan states: IDLE → SCANNING → DONE
  • Session tag collection: Polls BleTagDetector.getSessionTags() every second during a 10-second scan
  • Tag enrichment: Checks if each discovered tag is already mapped and attaches the tool name
  • Barcode processing: Determines if barcode is ELA C ID or Hilti decimal, converts to storage format
  • Duplicate prevention: Queries Firebase before assigning; blocks if tag already mapped
  • Cache refresh: Triggers BleTagDetector.refreshTagCache() after mapping

ToolsListViewModel

  • tools – StateFlow<List<Tool>> from repository, auto-updates
  • addToolWithName(name) – creates tool with no tag
  • deleteTool(id) – removes a tool
  • unmapTag(id) – unlinks tag and refreshes BLE cache
  • clearAllLastSeen() – resets all tool locations
What is StateFlow? A special type of Flow that always holds a current value. UI components observe it and automatically re-render when the value changes. It's like a "live variable" that the UI watches.

12. Background Execution Strategies

Keeping a BLE scanner running reliably in the background is one of the hardest problems on Android. The system actively kills background processes to save battery. This section summarises every strategy the app uses.

Foreground ServiceShows persistent notification; system won't kill the processRequired for continuous BLE scanning
